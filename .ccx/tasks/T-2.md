# Issue buffer folding — body / comments / attachments

## Goal

Long issues currently scroll forever — the body, every comment, the
attachment list, and the relations list all sit at top level. Add
section-level folds so the user can collapse what they don't need.
The CLI display already emits markers (`▾ 본문`, `▾ 코멘트 (N)`,
`▸ 첨부 (N)`, `▸ 관련 (N)`) — wire nvim's fold engine to those
markers.

## Acceptance

- [ ] Issue buffer (`filetype = redmine-issue`) sets `foldmethod`,
      `foldexpr`, `foldlevel`, and `foldtext` to produce one fold
      per top-level section: header (lines before first ▾/▸),
      `▾ 본문`, `▾ 코멘트 (N)`, `▸ 첨부 (N)`, `▸ 관련 (N)`.
- [ ] The CLI already indicates intended initial state via the
      glyph (`▾` = open, `▸` = closed). The buffer SHOULD honor it:
      sections starting with `▾` open by default, sections starting
      with `▸` closed by default. Implement via a one-shot post-
      render pass that calls `zc` on `▸` sections, NOT by hand-
      rolling a foldlevel scheme.
- [ ] Standard fold keymaps (`za`, `zo`, `zc`, `zM`, `zR`) all
      work without extra binding — this comes for free once
      foldmethod/foldexpr are set, but verify it.
- [ ] `foldtext` returns the section header line unchanged (don't
      decorate with `... N lines` boilerplate — the section title
      already includes the count, e.g. `▾ 코멘트 (7)`).
- [ ] Hard refresh (`R` key) preserves fold state if technically
      easy; if not, accept that refresh re-applies defaults. Note
      the choice in commit message.
- [ ] E2E: open issue #1 (which has comments + attachment), assert
      buffer has ≥ 3 folds via `vim.fn.foldclosed(lnum)` /
      `vim.fn.foldclosedend(lnum)`.

## Context

- `lua/redmine/ui/issue.lua` — `render`, `bind_keys`, `lock_buffer`
  helper from `util.lua`. Currently `set_lines` overwrites the
  whole buffer; folds need to apply AFTER set_lines.
- CLI render output format (see `redmine-core/src/redmine_core/render.py`):

  ```
  #1 — 제목
  상태 : … 진척 : …
  …
  (blank)
  ▾ 본문
    …body lines indented 2 spaces…
  ▾ 코멘트 (N)
    ─── author  date ───
      …
  ▸ 첨부 (M)
    - [#id] filename (XB)
  ▸ 관련 (K)
    - kind: #a ↔ #b
  ```

  Section header pattern: `^[▾▸] (본문|코멘트|첨부|관련)` — anchor
  on the glyph, not the Korean word, in case the CLI ever
  internationalizes.

- `syntax/redmine-issue.vim` — read it to confirm syntax already
  highlights the glyphs (don't break highlighting when adding
  fold expression).
- Don't use `foldmethod=marker` — the CLI output has no `{{{` /
  `}}}` markers and adding them is noise. Use `foldmethod=expr`
  with a small `foldexpr` function that returns `>1` on section
  header lines and `1` elsewhere.

## Out of scope

- Per-comment folds. One fold per section is enough.
- User-configurable fold defaults (`foldlevel` config option) — keep
  defaults baked.
- Changing the CLI render output. The glyphs and structure are
  fixed.
- New keymaps. Standard `za`/`zo`/`zc` cover it.

## Test plan

- Manual: `nvim -u tests/minimal.lua -c 'Rm 1'` →
  `▾ 본문` open, `▾ 코멘트 (N)` open, `▸ 첨부 (1)` closed.
  `zc` on body line collapses body. `zR` opens everything. `zM`
  closes everything (header excepted).
- E2E (add to `tests/run_e2e.lua`):

  ```lua
  -- Issue buffer applies folds to sections
  vim.cmd('Rm 1')
  wait_until(function()
    local b = vim.fn.bufnr('redmine://issue/1')
    if b == -1 then return false end
    local lines = vim.api.nvim_buf_get_lines(b, 0, -1, false)
    for _, ln in ipairs(lines) do
      if ln:match('^▸ 첨부') or ln:match('^▾ 첨부') then return true end
    end
    return false
  end, 8000)

  local b = vim.fn.bufnr('redmine://issue/1')
  -- Find any section header line and assert fold info there.
  local lnum_attach
  local lines = vim.api.nvim_buf_get_lines(b, 0, -1, false)
  for i, ln in ipairs(lines) do
    if ln:match('^[▾▸] 첨부') then lnum_attach = i; break end
  end

  local fold_start
  vim.api.nvim_buf_call(b, function()
    fold_start = vim.fn.foldclosed(lnum_attach)
  end)
  record('첨부 section is closed by default', fold_start ~= -1)
  ```

## Decisions

- q: "foldmethod = expr or syntax?"
  a: "expr. The glyph-only marker pattern is simple enough that
      foldexpr is more direct than embedding syntax fold regions.
      Syntax fold also fights re-render."
- q: "Should refresh preserve fold state?"
  a: "Best-effort. If the simplest implementation re-applies
      defaults on hard refresh, accept that. Don't write extra
      bookkeeping just for this."
- q: "Add user config for default fold level?"
  a: "No. The CLI already encodes intent via ▾/▸. Hand control to
      `set foldlevel=N` if a user really wants it."
- q: "What if syntax/redmine-issue.vim breaks with foldexpr?"
  a: "It shouldn't — foldexpr is orthogonal to syntax. If there's
      a conflict, escalate. Do not silently disable syntax."
