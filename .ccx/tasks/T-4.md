# Compose scaffold reference — status / progress / assignee hints

## Goal

Today `:Rmcomment <id>` opens a compose buffer with empty `status:` and
`assignee:` frontmatter fields and no hint about what valid values
would be. Users don't know whether the fields are required, what enum
values the server accepts, or who is reasonable to assign.

This task adds a **reference section** to the area BELOW the existing
`CUTOFF_LINE` so the editable frontmatter UX is unchanged but the user
can scroll down once to see:
- allowed statuses for this issue (id + name + `*` for closed)
- progress guidance (it's a 0..100 integer, not an enum)
- assignee candidates (the issue author + recent journal users)

Everything below the cutoff is already ignored by `redmine post --file`
(see `compose.lua` line 10 + `frontmatter.lua` body-cutoff logic), so
this is read-only context with zero risk to the post path.

## Acceptance

- [ ] Compose scaffold (`lua/redmine/ui/compose.lua` `scaffold()`)
      appends a **Reference** section AFTER the existing
      `<!-- ━━━ 아래는 참고용. post 시 무시됨. ━━━ -->` cutoff line
      and BEFORE the task-md context. Three subsections in this order:
      `## 가능한 status`, `## progress`, `## assignee 후보`.
- [ ] `## 가능한 status` lists the issue's allowed statuses as
      `- {id}: {name}{*}` lines, one per status (`*` suffix when
      `is_closed == true`). Source: `redmine meta statuses --issue <id>`
      (async, single call). On failure (network, CLI error), the
      section body is replaced with the single line
      `_(status fetch failed — :checkhealth redmine 확인)_` and
      scaffold rendering continues normally.
- [ ] `## progress` body is a fixed two-line block:
      `0 ~ 100 정수. UI 관례: 0/10/20/.../100.`
      `예: progress: 50`
      (No CLI call — progress is documented as a free 0..100 integer in
      `redmine-core/.../cli.py:162`.)
- [ ] `## assignee 후보` lists:
      - `- 작성자: {name}` (issue author — always present)
      - `- 참여자: {name1}, {name2}, ...` (unique users from
        `journals[].user`; omit line if zero participants)
      - `- 전체 멤버: redmine meta members --project <key>` (literal
        pointer; project key comes from the issue's `project.identifier`)
      - `- 빈 값 / none / unassign / - → 할당 해제` (literal hint)
      Names are display names; **no `@` prefix**, since `_resolve_user_id`
      already accepts names case-insensitively (`cli.py:110`). The
      author + journal participants come from the issue JSON that the
      worker fetches with `redmine fetch --id <id> --format=json`
      (existing wiring — see `compose.lua` `open()` if extended;
      otherwise add ONE async call here).
- [ ] **Frontmatter editing area is unchanged.** The first 5 lines of
      the buffer are still `---` / `id:` / `status:` / `assignee:` /
      `---`. No new keys, no inline `#` comments (the Lua frontmatter
      parser at `frontmatter.lua:24-29` does NOT strip `#` comments;
      adding any would leak into post payloads).
- [ ] Post behavior is byte-identical to pre-T-4: a `:Rmpost` on a
      scaffolded-but-untouched draft posts nothing (cutoff still
      separates editable from reference; existing
      `composed.body == ''` + no field-change short-circuit at
      `compose.lua:97` still fires).
- [ ] Config knob `compose.reference_section = true|false` in
      `config.lua` (default `true`). When `false`, scaffold is
      byte-identical to pre-T-4. Knob defaults must not break existing
      `setup({})` users.
- [ ] Existing 45 E2E cases stay green.
- [ ] At least **3 new E2E assertions** in `tests/run_e2e.lua`:
      1. Scaffolded buffer contains a line matching `^## 가능한 status$`
         AND at least one `^%-%s%d+:%s%S` line beneath it.
      2. Scaffolded buffer contains `## assignee 후보` AND the issue
         author's name on a `^%-%s작성자:` line.
      3. `compose.reference_section = false` makes the new sections
         disappear (scaffold contains no `^## 가능한 status$` line).

## Context

- Scaffold lives at `lua/redmine/ui/compose.lua` `scaffold()` (line ~23).
- `CUTOFF_LINE` constant at `compose.lua:10` — the contract for "below
  this line, the CLI ignores everything".
- The existing scaffold already appends task md below the cutoff
  (`lines.task_md` loop at the bottom of `scaffold()`). Reference
  section sits BETWEEN the cutoff and the task md — same fold/visibility
  semantics.
- CLI status query: `redmine meta statuses --issue <id>` returns
  `[{id, name, is_closed}, ...]` filtered to this issue's workflow.
  See `redmine-core/src/redmine_core/cli.py:131-142` (`cmd_meta`).
- CLI accepts both numeric id and name for status (`cli.py:98
  _resolve_status_id`) and assignee (`cli.py:110 _resolve_user_id`).
  Reference must convey BOTH paths so users can pick their preference.
- Issue JSON shape: `{id, subject, author: {id, name}, journals: [{user: {id, name}, ...}], project: {identifier, name, ...}, ...}`.
  Author + journals already come down with the existing
  `redmine fetch --id <id> --format=json` call; check whether
  `compose.lua` currently fetches them — if not, add ONE async call.
- Async pattern: see `cli.run_allow_fail` (already used at
  `compose.lua:239` for the suggested-assignee path). Same pattern for
  the meta-statuses fetch. Render scaffold with placeholder + replace
  the section body on callback (or block until both come back — both
  are fine; pick the simpler one and document the choice in
  `## Decisions` below).
- Existing `suggested_assignee` plumbing must be preserved (it
  pre-fills `assignee: <last commenter>` in the editable frontmatter).

## Out of scope

- Any change to the editable frontmatter region (id/status/assignee).
- Any change to the frontmatter parser (`lua/redmine/frontmatter.lua`).
  Inline `#` comments support is explicitly NOT being added — that
  belongs to a future task if ever.
- New CLI subcommands. `redmine meta statuses --issue` already exists.
- Picker integration in the compose buffer (e.g. `<leader>ss` to insert
  a status from a picker into the frontmatter). Out of scope for T-4 —
  may be revisited later.
- Reference section refresh on `:Rmfetch` / hard refresh. The scaffold
  is generated once at `:Rmcomment` time and that's enough for M4.

## Decisions

- q: "Where does the reference section sit — above or below the
     cutoff?"
  a: |
    Below. The cutoff already means "ignored by post". Putting reference
    above the cutoff would require frontmatter-parser changes to skip
    it, which is explicit out-of-scope (frontmatter parser is fragile
    and the # inline comment problem is documented).

- q: "Should the reference section render synchronously (block scaffold
     until meta statuses returns) or asynchronously (render scaffold
     with placeholder, replace on callback)?"
  a: |
    Async with placeholder is preferred (snappier UX, scaffold visible
    immediately). The placeholder body for `## 가능한 status` is
    `_(loading...)_` and is replaced atomically when the meta call
    returns. On error, replace with `_(status fetch failed — :checkhealth redmine 확인)_`.
    If async adds significant complexity, sync is acceptable — the
    block on a single meta call is typically <300ms. Document the
    choice in the commit message.

- q: "What about issues with no allowed_statuses (empty workflow
     response)?"
  a: |
    The CLI already falls back to `client.list_statuses()` when
    `allowed_statuses` is empty (`redmine-core/.../cli.py:135-137`).
    Trust that; render whatever the CLI returns. If the list is still
    empty (extremely unusual — would mean Redmine has zero statuses
    defined), render `_(no statuses returned — check Redmine config)_`.

- q: "Should the assignee candidates list include the CURRENT assignee
     of the issue too?"
  a: |
    Yes, implicitly — `## 작성자` covers author and `## 참여자` covers
    journal users. The CURRENT assignee, if any, will almost always
    appear in journals (they were assigned at some point). Explicitly
    listing assigned_to too would risk dup; just dedup the participant
    set against author and skip the explicit current-assignee line.

- q: "Do we need to handle the case where compose.reference_section is
     missing from a user's config?"
  a: |
    Yes. The config-merge in `lua/redmine/config.lua` should default
    the key to `true` so existing setup tables work without change.
    The new key lives under the existing `compose` table.
