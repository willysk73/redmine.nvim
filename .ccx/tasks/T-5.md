# Pending posts buffer + `:Rm` fallback + `:Rmpost` extensions

## Goal

Drafts already persist on disk at
`{worktree}/.redmine/drafts/comment-draft-{id}.md` (see
`redmine-core/.../paths.py:16`); a successful post moves the file to
`{worktree}/.redmine/posted/` (see `compose.lua:114`). So the **local
staging area already exists**, but there is no UI to see what's
sitting there, post all of it, or discard a draft without opening it.

This task surfaces that staging area as a fugitive-style **pending
buffer**: `:Rm` (no arg, no detected issue id) opens a read-only
listing of pending drafts with per-draft change summary, keymaps for
post / discard / open, and a `:Rmpost` argument surface for non-buffer
flows. The pre-existing `:Rm` paths (`:Rm <id>` and `:Rm` with branch-
detected id) are **unchanged**.

## Acceptance

### Pending buffer

- [ ] New file `lua/redmine/ui/pending.lua` exporting `M.open()` and
      `M.refresh(bufnr)`. Buffer name `redmine://pending`, `filetype =
      'redmine-pending'`, modifiable=false, swapfile=false.
- [ ] Buffer contents: header line + one block per draft. Header:
      `Pending Redmine posts — {drafts_dir}  ({N})`. Per-draft block
      (3 lines):
      ```
      #{id}  {first 60 chars of frontmatter id-line or "(unknown)"}
        [{change-summary}]
        > {first non-empty body line, max 80 chars, ellipsized}  · {lines} lines · {mtime}
      ```
      `change-summary` is built from frontmatter (using existing
      `lua/redmine/frontmatter.lua`):
      `status: X` (when non-empty), `progress: N`, `assignee: Y`,
      `time: H`. Multiple changes joined with `, `. If no fields set:
      `no field change`.
- [ ] **Empty state** (no `.md` files in drafts dir, or dir missing):
      buffer renders the header `Pending Redmine posts — {drafts_dir}  (0)`
      followed by a blank line and:
      ```
      No pending posts.
      :Rmcomment <id>   — start a new draft
      :Rminbox          — open inbox (or press i)
      ```
      Cursor lands on the first command-line.
- [ ] Keymaps (buffer-local, normal mode):
      - `<CR>` → open the draft under cursor in compose buffer (use
        existing `lua/redmine/ui/compose.lua` open path; reuse
        `cli.run({'path','draft','--id',<id>}, ...)` or just open the
        file directly since the listing already has its path).
      - `p` → post the draft under cursor (call existing
        `compose.post_file(path)` helper; create that helper if not
        already exported — it should be a small refactor of the
        existing `post_buffer` body that takes a file path instead of
        a buffer number).
      - `P` → post ALL listed drafts sequentially. Failures don't
        abort the loop. Final `vim.notify` summarizes `M posted, N
        failed` (failures get an additional ERROR notify each with
        the file path so the user can inspect).
      - `d` → discard the draft under cursor. Prompts via
        `vim.fn.confirm('Discard draft for #{id}?', '&Yes\n&No', 2)`;
        on Yes, `vim.fn.delete(path)` and refresh.
      - `r` → re-scan drafts dir and re-render.
      - `q` → close the buffer.
      - `i` → `vim.cmd('Rminbox')`.
- [ ] After `p` / `P` / `d`, the buffer auto-refreshes (so the entry
      that just got posted/discarded disappears).

### `:Rm` fallback change

- [ ] `:Rm` (no arg, **no** detected issue id from cwd/branch) →
      opens the **pending buffer** (was: inbox).
- [ ] `:Rm <id>` → unchanged (open that issue).
- [ ] `:Rm` (no arg, detected id from cwd/branch) → unchanged
      (open that issue).
- [ ] `:Rminbox` → unchanged (always opens inbox explicitly).

### `:Rmpost` argument surface

- [ ] `:Rmpost` (no arg) — preserve existing behavior: post the
      current compose buffer if cursor is in one. If cursor is in the
      pending buffer, treat as the `P` keymap (post all). Otherwise
      ERROR notify: `:Rmpost — compose 또는 pending 버퍼에서 호출하거나, :Rmpost <id> / :Rmpost all 사용`.
- [ ] `:Rmpost <id>` — post the draft file for `<id>` without opening
      it. ERROR if no draft file exists for that id.
- [ ] `:Rmpost all` — post every draft in the drafts dir (same loop
      as `P`).
- [ ] `:Rmpost` argument completion: `<Tab>` suggests `all` plus every
      id with a pending draft (one for each `comment-draft-{id}.md`).

### Config + housekeeping

- [ ] `config.lua` gains an optional `keymaps.pending_buffer` subtable
      (mirrors the existing `keymaps.inbox_buffer` shape) with the
      defaults above. Users can override individual keys.
- [ ] No new top-level `Setup` keys outside the existing `keymaps`
      tree.
- [ ] Existing 45 E2E cases stay green.
- [ ] At least **4 new E2E assertions** in `tests/run_e2e.lua`:
      1. With drafts dir empty, `:Rm` (no arg, no detected id) opens
         a `redmine://pending` buffer whose first line matches
         `^Pending Redmine posts —`.
      2. Seed 2 drafts (write 2 files into the drafts dir directly,
         frontmatter only — `id: 1` with `status: Resolved`, and
         `id: 2` with empty fields), refresh, assert both `#1` and
         `#2` lines render, and `#1`'s block contains `status: Resolved`.
      3. Press `p` on the `#1` line (use `vim.api.nvim_input` or call
         the keymap action directly), assert the file moved from
         `drafts/` to `posted/` and `#1` is gone from the rendered
         buffer.
      4. `:Rmpost all` from a non-buffer context (e.g. from an inbox
         buffer) posts the remaining draft and the drafts dir ends
         empty.

## Context

- Existing path resolution: `redmine path draft --id <id>` from the
  CLI returns the draft file path; same path is also computable
  client-side from config (faster). Drafts dir =
  `vim.fn.fnamemodify(<one draft path>, ':h')` or via
  `redmine path archive --id <id>` then `:h:h`. The simpler approach
  is a single `redmine path draft --id 0` call once at buffer open
  (the path templates don't really vary by id at the dir level — id
  appears in the filename, not the dir).
- Existing `:Rm` dispatch lives in `lua/redmine/commands.lua`
  (`rm_command` ~line 60-80). Detection: see how it currently picks
  between issue buffer and inbox fallback; insert the new fallback
  there.
- Existing post path: `lua/redmine/ui/compose.lua` `post_buffer()`
  (line 68). Extract the file-given post path into a `post_file(path)`
  helper that `post_buffer` then calls; the pending buffer's `p`/`P`
  reuse it. Surgical refactor — do NOT rewrite `post_buffer` beyond
  this extraction.
- Existing inbox buffer pattern: `lua/redmine/ui/inbox.lua` —
  buffer setup, filetype, keymap binding, refresh function. Mirror
  this pattern for `pending.lua`.
- `lua/redmine/frontmatter.lua` parser returns `composed.fm` with
  `id`, `status`, `progress`, `assignee`, `time` keys; empty values
  are normalized to `nil` (`frontmatter.lua:28`). Build the change
  summary by iterating those keys in fixed order.
- `mtime` formatting: `os.date('%H:%M', mtime)` if same day, `%m-%d`
  if same year, `%Y-%m-%d` otherwise. Keep it short.
- Post sequencing: use `cli.run` and chain via callback (the existing
  `compose.post_file` will be async). For `P` / `Rmpost all`, post
  them one at a time so failures of one don't kill the in-flight
  state of others. Track a `(posted, failed)` counter; final notify
  fires when all callbacks have returned.

## Out of scope

- Parallel posts. Sequential only.
- Draft creation from inside the pending buffer (use `:Rmcomment <id>`).
- Issue-title lookup in the listing. The frontmatter only carries
  `id`; fetching the title would require a network call per id, which
  is too expensive for a refresh that runs on every `r`. The first-
  line preview shows the body which is enough context.
- Autocmd-driven auto-refresh (BufWritePost on a draft file). Manual
  `r` only. Adding an autocmd is a small follow-up — surface as a
  `chat_ask` if you actually need it for the E2E tests.
- Recoverable discard (`.trash/` instead of `rm`). The drafts dir
  lives in gitignored `.redmine/`, so there is no recovery either way;
  `rm` with confirm is honest about that.
- Changes to the existing inbox buffer or its keymaps.
- Status-bar / lualine integration.

## Decisions

- q: "When `:Rm` (no arg) is invoked and the cwd has a detectable
     issue id (e.g. branch name `issue-123`), should it still go to
     the issue buffer or to pending?"
  a: |
    Issue buffer (unchanged). The user explicitly chose this in
    conversation: `:Rm <id>` and detected-`:Rm` both open that
    issue; only the failed-detection fallback flips from inbox to
    pending. Rationale: when you're working on a branch tied to a
    specific issue, opening that issue is more useful than seeing
    the pending list.

- q: "Should the empty pending buffer immediately redirect to inbox
     (skip showing the empty pending screen)?"
  a: |
    No. The user explicitly picked option A in conversation (show the
    empty pending screen with `:Rminbox` and `:Rmcomment <id>` pointers
    plus `i` keymap). Rationale: predictable `:Rm` behavior is more
    important than saving one keystroke; flipping target buffer based
    on dir contents would be confusing.

- q: "Should `P` (post all) bail on the first failure or continue?"
  a: |
    Continue. Sequential, fail-soft. Each failure produces an ERROR
    notify with the file path; the loop continues with the next file.
    Final summary `M posted, N failed`. Rationale: a single bad draft
    (e.g. invalid frontmatter) should not block the rest.

- q: "Should `d` (discard) move the file to `.trash/` or `rm` it?"
  a: |
    `rm` with a `vim.fn.confirm` prompt. The drafts dir is inside
    gitignored `.redmine/`, so there's no version-control safety net
    either way. A trash directory would be a speculative feature
    (it'd need a separate cleanup story); honest rm is simpler.

- q: "Does `:Rmpost <id>` need a confirm prompt like the in-buffer
     post path?"
  a: |
    Same rule as the existing `:Rmpost`: honor `config.compose.confirm_post`.
    Default is to confirm; user can opt out via `confirm_post = false`.
    `:Rmpost all` runs the same confirm BEFORE the loop (one prompt
    listing how many drafts will be posted), not per-draft.

- q: "Should the listing show drafts sorted by mtime (newest first)
     or by id?"
  a: |
    By mtime, newest first. Matches `git log` / fugitive's
    convention. Id-sort would surprise users who expect their most
    recent work at the top.
